# Release facts

Machine-extracted, changelog-independent records of what each DocumentDB release
actually contains, derived from the source code at the release's git tag.

## Why

`CHANGELOG.md` in the source repo tracks internal release trains, not the OSS tags:
sections are amended after tags are cut (the v0.114-0 section gained entries for
commits that are not in the v0.114-0 tag), detailed entries have been rewritten with
information lost, and real behavior changes (e.g. the `documentdb.enableBypassDocumentValidation`
default flipping to `true` in v0.114-0) are sometimes not recorded at all. The only
reliable record of a release is the code at its tag, so docs updates are driven from
these extracted facts instead of the changelog.

## Layout

- `v<version>.yml` — full fact inventory for one tag: GUCs (name, type, default,
  min/max, description), gateway wire commands, aggregation stages, expression
  operators, gateway `DOCUMENTDB_*` environment variables, and SQL functions.
- `deltas/v<version>.md` — the true delta from the previous tag, generated by
  diffing two fact files. This is the docs-update checklist for a release: every
  line is a surface that may need a page created, removed, or re-annotated.

## Regenerating

Requires Python 3.10+ with PyYAML, and a clone of
[documentdb/documentdb](https://github.com/documentdb/documentdb) (any state; files
are read at the requested ref via `git archive`, the working tree is not touched).

```bash
python scripts/extract_release_facts.py --source ../documentdb --ref v0.114-0
python scripts/diff_release_facts.py release-facts/v0.113-0.yml release-facts/v0.114-0.yml \
    --out release-facts/deltas/v0.114-0.md
```

## What is extracted, and from where

| Surface | Source of truth |
| --- | --- |
| GUCs | `DefineCustomBool/Int/Real/String/EnumVariable` calls in `pg_documentdb`, `pg_documentdb_core`, `pg_documentdb_extended_rum` (C sources and headers); `DEFAULT_*` macros are resolved to their values |
| Wire commands | `RequestType::*` arms dispatched in the gateway's `processor/process.rs`, mapped to wire names via `requests/request_type.rs` |
| Aggregation stages | `StageDefinitions[]` in `aggregation/bson_aggregation_pipeline.c` |
| Expression operators | `OperatorExpressions[]` in `operators/bson_expression.c`; entries with `NULL` parse and handler functions are marked `implemented: false` |
| Gateway env vars | `"DOCUMENTDB_*"` string literals in gateway Rust sources (test code excluded) |
| SQL functions | `CREATE FUNCTION/PROCEDURE` in `*--latest.sql` UDF scripts |

## Known limitations (prototype)

- Accumulators, window operators, query operators (`$eq`, `$elemMatch`, ...) and
  update operators (`$set`, `$inc`, ...) are not yet extracted — they live in
  separate parse tables and should be added as further surfaces.
- The `internal/` tree (`pg_documentdb_distributed`) is deliberately excluded; it is
  not part of the shipped OSS packages.
- Enum GUC option lists are not captured (only the default symbol).
- A dispatched command is not proof of full support (some arms return constant or
  "not supported" responses); pair with per-command behavior checks before
  documenting.
- SQL function extraction reads only `*--latest.sql` fragments; functions defined
  exclusively in versioned migration scripts are not listed.

## Planned follow-ups

1. CI check: every GUC name, default, function, or env var mentioned in a docs page
   must exist in the facts file for the version the page claims.
2. Generated reference pages (full configuration reference, command/operator support
   matrix) built from these fact files instead of hand-written long-tail pages.
3. Changelog cross-check lint: flag CHANGELOG bullets naming GUCs/functions that do
   not exist in the tag they are filed under.
